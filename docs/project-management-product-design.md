## 1. 需求与已确认决定

每天的 Task 和 Task Log 已经能记录工作，但缺少长期归属：用户难以知道这些工作在推进哪个技术方向或负责的系统，具体目标投入了多少、完成到什么程度，以及后续应该把时间放在哪里。

本轮确认采用两层管理结构：第一层是“方向”，第二层是“里程碑”。Task 关联第二层，日志和工作时段随 Task 汇总。两层都需要统计，总体概览默认以里程碑的投入与完成情况为主体，服务于后续投入决策。

| 决定 | 状态 | 含义 |
| --- | --- | --- |
| 方向 → 里程碑两层管理 | 用户已确认 | 方向承接技术大方向或负责的系统；里程碑承接自己规划的目标或被交代的具体项目 |
| Task 与第二层关联 | 用户已确认 | 日常工作落在里程碑上，再向上汇总到方向 |
| 两层均提供统计 | 用户已确认 | 既看具体里程碑投入，也看整个方向的投入分布 |
| 总体概览默认看里程碑 | 用户已确认 | 结合投入与完成情况，判断接下来继续、调整还是减少投入 |
| KTLO 单独作为方向 | 用户明确偏好 | 临时维护与支持在方向层单独统计；其下如何承接碎片任务仍为设计建议 |
| Task 是否限一个主里程碑 | 建议，待讨论 | 本稿先按零或一个主里程碑设计，以保持计时可加总 |
| 历史归属跟随整体重分类 | 建议，待讨论 | Task 或里程碑改归属时，历史实时汇总一并变化 |
| 里程碑由用户确认完成，Task 辅助验收 | 建议，待讨论 | 不要求创建时拆完 Task，不因 Task 全完成自动认定成果已达成 |
| 每周工作提升节奏 | 材料中的试行建议，待用户采用 | 四周试行、每周约 100 分钟；作为现有层级上的计划和复盘方式，不是新管理层级 |

这里的“里程碑”可以持续一段时间、包含多个 Task、有预期成果；一个具体项目可以直接作为一个里程碑。两层之间及里程碑之下不增加另一层 Project。针对 KTLO 日常支持，本稿另建议一个同层的持续承接项，见第 4.4 节；此例外尚未确认，不冒充可完成的成果目标。

设计原则：方向负责长期归属与资源回顾；里程碑负责目标、成果和推进；Task 负责可执行的工作；Task Log 保存过程证据；Work Session 保存已记录投入。日常仍使用原来的 Task、Focus 和日志，管理视图自动聚合。

## 3. 两层产品模型

### 3.1 方向（Area）：长期关注或负责的范围

方向可以是一项技术大方向，也可以是自己负责的系统。它回答“我在哪些长期范围内工作，各方向投入是否符合当前重点”。一个方向可以容纳多个里程碑，包括同时推进和已经结束的里程碑。

建议基本信息：名称、职责或长期关注点、可选优先级、当前重点、可选回顾日期。方向可以暂停或结束跟踪，也可以归档恢复；具体状态名称尚未定稿。

方向没有整体完成百分比。方向页可以显示里程碑的状态分布、已确认成果、近期重点和投入，但不把里程碑完成率平均成方向完成率，也不因所有现有里程碑结束而自动结束方向。

### 3.2 里程碑：承接具体目标和项目

里程碑回答“这一段时间要做成什么，已经投入多少，现在做到了哪里”。它既可以来自自己的规划，也可以来自他人交代的具体项目；不因来源不同再增加产品层级。

建议基本信息：名称、所属方向、目标、可选完成标准、优先级、可选目标日期，以及当前成果、下一步和阻碍。可选每周投入目标用于投入回顾，不是完成度。

建议一个里程碑属于一个方向。里程碑之下直接关联 Task；需要细化验收时，可选填写轻量检查项。检查项只是目标内容，不拥有独立 Task 归属、工时或下级对象，不成为第三层管理对象。

例如，以下均为结构说明：

| 方向 | 里程碑 | 关联 Task 示例 |
| --- | --- | --- |
| Chronicle 系统 | 引入项目制并完成日常使用验证 | 讨论产品设计；实现任务归属；核对投入统计 |
| Chronicle 系统 | 改善数据可靠性 | 排查保存冲突；补齐备份恢复流程 |
| 技术能力建设 | 完成一次指定主题的技术分享 | 阅读资料；制作演示；进行试讲 |

创建应保持轻量。建议方向名称必填；里程碑名称和所属方向必填，其余可以稍后补充。没有填写目标或完成标准时如实提示，不阻止先记录工作，也不自动生成完成判据。

### 3.3 Task、日志和投入的关系

以下关联基数是建议，尚待用户确认：

- 一个 Task 可以暂不归属，也可以关联一个主里程碑；方向从里程碑继承，不再重复选择。
- 一个 Task 可以跨天、跨周继续工作，不要求每天重建同一个工作对象。
- Task Log 通过 Task 出现在所属里程碑的动态中；方向可聚合查看，不要求每次写日志再选归属。
- Work Session 通过 Task 计入里程碑，再汇总至方向，不另开方向或里程碑计时器。
- Tags 继续表达 research、bug、meeting 等工作性质，不产生另一份投入。KTLO 按用户偏好成为一个方向，旧 ktlo 标签仍可保留，但不能替代正式归属。
- 共享工作首版建议选一个主里程碑；必要时拆成可独立计时的 Task。文字或证据可以链接多个目标，但链接不分摊工时。

里程碑不会被实现成一个超级 Task，也不要求把具体工作的日志再复制一份。

### 3.4 生命周期与归档

建议里程碑状态为：筹备中、进行中、暂停、已完成、已取消。完成由用户确认，可以重新打开；取消与完成分开，均保留此前投入和成果。

方向与里程碑分别归档。归档只控制日常列表可见性，不等于完成、取消或删除，可以恢复；历史查询仍可找到。归档方向时如仍有活跃里程碑，界面展示提醒和影响，由用户明确处理，不静默归档下层。

方向、里程碑和 Task 的状态互不级联：暂停方向不自动暂停其里程碑；暂停里程碑不批量改 Task；完成 Task 不自动完成里程碑。结束里程碑时展示未完成和正在计时的 Task，供用户处理，不自动批量关闭或删除。

建议历史修订和补记保持可用，新工作应先重新打开已结束的里程碑。首版以归档替代方向和里程碑删除，不提供已有投入的级联删除入口。

## 4. 增改查和日常关联

### 4.1 创建、编辑和查询

“项目管理”作为功能入口，默认打开里程碑总览，同时提供方向视图。入口名称是界面建议，不代表增加一个 Project 实体。

用户可以先创建方向，再在方向下创建里程碑；也可以从总览新建里程碑时选择或快速创建方向。里程碑创建后可关联已有 Task，或直接创建 Task，不强制先写完目标或拆解验收检查项。

两个层级均支持编辑、按名称或描述搜索、状态筛选和归档查询。里程碑列表额外支持方向筛选。全局搜索应能分别返回方向和里程碑，显示层级帮助识别同名项。

目标、完成标准、归属和状态的重要变化进入动态；改名和一般编辑不自动视为成果。里程碑调整所属方向会影响向上的统计，历史处理见第 4.3 节。

### 4.2 让归属进入已有录入路径

| 入口 | 推荐行为 |
| --- | --- |
| 里程碑内创建 Task | 自动填入当前里程碑，显示所属方向，可修改 |
| 方向内创建 Task | 在该方向的里程碑中选择；没有合适对象时可快速创建里程碑或暂不归属，不直接把 Task 挂到方向 |
| 从已有 Task 续建 | 继承里程碑并链接前后任务；改到其他里程碑继续时显式选择 |
| 全局创建 Task | 里程碑可选，按方向组织并提供最近使用项；不根据上次选择静默归类 |
| Task 详情 | 标题附近展示“方向 / 里程碑”，可跳转和修改里程碑 |
| Board | 显示归属，支持方向/里程碑筛选和批量关联、移出 |
| Today / Focus | 候选 Task 显示归属；继续引用 Task；新建时可选里程碑 |
| 会议录入 | 确认时可选里程碑，会议 Task 的日志和已记录投入随之归集 |
| API / MCP 创建或更新 Task | 支持同一里程碑关系；旧调用不传归属仍可工作 |
| 向已绑定 Task 追加日志 | 沿用 Task 归属，不额外要求 agent 重复设置 |

“未归属”保留独立查询和批量整理入口，不打断每次快速记录。旧任务不自动按标签或 LLM 猜测分组。

### 4.3 历史归属：建议整体重分类，尚未确定

建议将 Task 从里程碑 A 改到 B 解释为“这项工作整体应归 B”：历史日志和全部已记录投入在实时视图中一起转到 B，并相应调整所属方向的汇总。首次给旧任务补里程碑按同一规则回填，不修改原日志、计时起止时间或 Task 身份。

保存前在同一编辑界面展示影响，例如：“该任务的历史日志和 12.4h 已记录投入将从 A 归入 B；里程碑及方向历史报表将重算。”同时展示日期范围、受影响方向及成果引用。建议保留变更历史并支持撤销，避免连续弹窗。

这适合纠正分类和首次整理。若工作从某天开始转向另一目标，建议提供“在另一里程碑继续”：预填新的后续 Task，选择目标，链接原 Task，保留旧任务历史；不复制旧日志或计时。不同时引入同一 Task 的按日期分账作为另一种默认模式。

里程碑从方向甲移到方向乙也存在同样问题。本稿建议其全部 Task 与历史投入跟随重分类，并在保存前展示两个方向的影响；这条规则同样待讨论，不能在用户未理解时静默调整。

已保存的周报或摘要是当时快照，不静默改写。重分类后提示实时数据已变化，可以重新生成。已确认的成果和历史决定不被静默删除；引用如何保留或改指向需在变更预览中说明，跨目标证据链接不产生额外工时。

### 4.4 维护、杂项和未归属的边界

用户倾向于把临时工作放进独立的 KTLO 方向。该方向与其他方向并列，显示本周、本月、累计投入，帮助识别日常保障占用了多少时间。

为保持 Task 仍关联第二层，同时不要求每个小请求创建同名里程碑，新增以下待讨论建议：

- KTLO 下设一个默认“日常支持”持续承接项。它与成果型里程碑处于同一层，Task 关联方式和计时一致，明确标识为持续事项，不显示完成率，也不计入“本周达成多少个成果里程碑”。
- 默认项长期复用，按周/月筛选投入即可；首版不增加自动月结、跨月任务迁移或周期关账。
- 有明确结束条件的事故整改、升级或支持专项，可以在 KTLO 下独立创建成果型里程碑，正常验收完成。
- KTLO 入口创建 Task 时可显式预选“日常支持”；其他入口不因临时出现、紧急或带标签而自动改归 KTLO。已经服务于明确目标的紧急工作仍可以留在原目标下。
- 持续承接项可在总览单独汇总或折叠，但它的投入不能从全局分母消失。

例如，“处理一次运行故障”可属于 KTLO；从故障中提出的系统性改进，如果成为独立目标，可以归入对应技术方向。分析可以引用原故障记录，历史抢修投入不因后续提出改进而自动搬走。

KTLO 作为方向后，同一项工作不再自动同时给原系统方向贡献工时。如需查看受影响系统，可用标签或参考链接补充；这是另一种观察视角，不能再加进方向总计。未归属依然保留，用于快速记录和后续整理。

“持续承接项”是本轮为 KTLO 提出的扩展，不属于用户已确认的里程碑完成规则。若用户希望第二层全部必须有明确终点，应进一步讨论替代方案。
## 5. 页面与日常决策

### 5.1 总体概览：默认看里程碑

用户已确认总体概览的主体是里程碑，以投入和完成情况帮助决定后续投入。建议默认展示活跃的未完成里程碑，包括本周零投入的目标，并保留本期有投入或完成的里程碑；已完成不直接隐藏。支持查看暂停、筹备和全部状态，提供置顶、优先级及本周投入排序；方向筛选和按方向分组方便切换视角。若本期有投入的归档项在日常列表中折叠，必须有明确可展开的分组解释其投入。

每一行或卡片建议显示：

- 里程碑名称、方向标识、优先级和完成状态。
- 本周已记录投入、累计已记录投入。
- 目标或完成标准摘要，以及最新已确认成果。
- 下一步、阻碍或当前风险说明。
- 可选目标日期；如设置每周投入目标，显示实际记录与目标的对照。

投入与成果并列展示，不压缩成一个自动分数。用户应能区分“本周投入很多但仍受阻”“已有成果、下一步明确”“目标已不再重要”等情况，再选择继续推进、提高或降低优先级、暂停或完成。自动调整优先级或安排后续任务不在首版默认行为中。

顶部可显示选定期间的里程碑投入分布，默认本周，可切换本月，并保留未归属。累计指标始终标注为累计，不能随本周筛选被误读为本周数值。方向作为标识、筛选和另一个汇总入口，不取代默认的里程碑主体。

本周没有时段时显示“本周未记录投入”，不能断言用户没有工作。仅计时变化、改标题或新建 Task，不刷新“最近成果日期”。任务完成数量只作工作清单信息，不当作里程碑完成率。

### 5.2 里程碑详情

| 视角 | 主要内容 | 要支持的决定 |
| --- | --- | --- |
| 概览 | 所属方向、目标、完成标准、当前状态、成果、下一步、阻碍、本周/累计投入 | 现在做到哪里，接下来如何投入？ |
| 任务 | 现有 Task，按状态查看；创建/关联任务 | 下一步执行哪件事？ |
| 进展 | 可选验收检查项、进展更新、任务日志与成果来源 | 做成了什么，还缺什么？ |
| 投入 | 日/周趋势、Task 分布、工作性质分布、累计投入和明细 | 时间花在哪里，是否值得继续？ |

打开 Task 复用已有详情工作区，返回时保留里程碑和筛选。成果可以链接现有 Note、Task Log 或外部交付物；首版不再建设一套文档编辑器。

### 5.3 方向详情：汇总长期范围

方向页显示职责或长期关注点、当前重点、本周/本月/累计已记录投入、下属里程碑的投入分布、状态分布和近期成果。可以从方向页新建或进入里程碑。

方向汇总帮助判断这一范围是否获得合适投入，以及内部哪些目标占用了时间；它不是一张有终点的总任务清单。不显示方向整体完成百分比，不将下属里程碑的人工比例平均，也不把检查项数量跨里程碑相加当成进度。

已结束或归档里程碑仍贡献历史投入。方向内默认可以只展示活跃里程碑，但统计必须能解释其他投入来源，避免列表可见项被误当作完整分母。

### 5.4 与 Today 和 Report 衔接

Today 保持执行入口，可按方向或里程碑筛选 Task。里程碑的“下一步”优先链接已有 Task，没有时可在上下文中创建；不自动往 Day Script 塞任务。

Report 增加方向和里程碑两个聚合维度，以及筛选和未归属分组。两个维度展示同一批时间的不同汇总层次，不将方向合计和里程碑合计再次相加。详情的投入数与 Report 使用同一统计期间、工作日设置和计时口径，支持方向 → 里程碑 → Task → 时段逐级核对。

## 6. 投入分析的明确口径

### 6.1 指标与两层汇总

主指标命名为“已记录投入”，数据来自 `work_sessions`。它衡量系统记录到的用户工作时间，不代表完整真实工作量、成果价值或 agent 的运行时间。

里程碑显示本周、本月、累计已记录投入，指定期间的日/周趋势及按 Task 的分布；方向由其里程碑向上汇总，显示同类指标和里程碑分布。若采用 KTLO 持续承接项，它使用相同计时方式并纳入第二层投入统计，但从成果完成数量中排除。方向和里程碑均可与同层对象比较，未归属单列。

在本稿建议的单一归属模型成立时：

- 一个里程碑的投入，等于其关联 Task 在同一期间的已记录工作时间之和。
- 一个方向的投入，等于其下里程碑及同层持续承接项在同一期间的已记录投入之和。
- 全部第二层对象投入之和加未归属，应等于同期间 Report 的已记录工作时间；全部方向投入之和加未归属也应相等。
- 上述两种全局合计是同一总量的两种分组，不是两份投入。

若设置“每周计划投入 6h”，显示“本周已记录 4h / 计划 6h”。这是一项用户设定的投入目标，不从 Focus 日程自动生成，也不称为里程碑完成度。是否需要同时在两层配置投入目标，仍待讨论；两层目标不能默认重复相加。

### 6.2 保持可以核对

- 按统计期间裁切时间段，沿用 Report 的时区、工作日起点、周起点；未结束时段只计到当前时刻。
- AFK、idle 不归入方向或里程碑投入，可在全局时间分析单独显示。
- 会议只按实际写入的工作时段计入，不再把原始会议跨度另加一次。
- Task Log 不产生分钟数；Focus 计划时长及首次编辑到提交的执行跨度不叠加到工作计时。
- 没有关联里程碑的 Task 投入单列“未归属”；其他遗留无法归属的计时记录同样保留，并可查看原因。
- 默认全范围的分布包含已结束或归档对象的历史时间，必要时明确合并展示为“其他里程碑”或“其他方向”；隐藏列表项不能隐藏其投入。
- 同层对象的全局占比分母是全部已记录工作时间，包含未归属，不是仅选中重点对象的总量，也不是在线时长。方向内部占比另行明确标注“占本方向”。
- 一个 Task 按建议只给一个主里程碑贡献时间，再汇总到所属方向。按标签分析会因多标签交叉而不可直接相加；可相加的工作性质图需明确互斥分类，例如会议优先、KTLO 次之、其他最后。
- 当前 Report 数值汇总不是通用的重叠区间去重器。实现时应共用统计规则，验证现有时段不重复；发现异常应暴露并修正共同口径，不能让新页面自行另算出不同总数。

删除已有 Task 当前会删除其时间和日志。管理页面应优先提供完成、取消、移出等操作；任何仍保留的 Task 永久删除入口都需要说明会减少里程碑及方向历史投入，并沿用现有删除确认。方向或里程碑的归档、暂停、取消本身不能造成历史消失。

## 7. 进度管理：里程碑的成果、判断和证据

### 7.1 完成标准和可选验收检查项

用户询问：里程碑由自己标记完成，还是在规划时创建全部 Task、由 Task 全部完成代表里程碑完成？本稿推荐“用户确认成果，系统辅助验收”。这项推荐仍待用户确认。

建议日常流程：

1. 创建时先写目标，能写清时补一句“怎样算完成”。可以只创建已明确的第一批 Task，不要求预先穷尽拆解。
2. 工作中照常创建、完成或取消 Task、追加日志；不用同步维护一份里程碑百分比。
3. 系统自动展示任务状态、已有成果和待处理项。全部相关 Task 完成时提供一次轻量“核对里程碑是否达成”的提示，不静默变更里程碑状态。
4. 用户随时可以点击“完成里程碑”，查看完成标准及现有证据后确认。能够引用已有日志/笔记，不强制再写一份总结。
5. 有未完成 Task 时展示列表和原因，允许用户决定保留、移到后续目标或取消；不能自动关闭这些 Task，也不必为了验收将任务机械清零。

辅助提示的边界：零个 Task 不代表 100%；DROPPED 不等于已完成；全部 Task 已结束但包含取消时，明确显示“已完成/已取消”区别。里程碑完成后再重开 Task 或新增工作，提示复核里程碑状态，不静默抹去之前的验收记录。

这不排斥任务清单已经完全覆盖目标的简单场景：此时用户核对后可直接确认。首版不增加需要单独管理的“关键 Task”、必选验收映射或自动完成模式。状态、完成标准和证据是基础，可选检查项用于有需要的目标。

例如里程碑“引入项目制并完成日常使用验证”，可以填写以下验收检查项：

- 方向和里程碑可以创建、编辑和查询。
- 新旧 Task 可以正确关联到里程碑。
- 两层投入与 Report 能够核对。
- 能依据成果、当前状态和下一步安排后续工作。

这些是一个里程碑的完成标准细化，不是新的里程碑或子项目。检查项可以引用 Task、Task Log、Note 或交付物，但不拥有独立工时，也不强制给每个 Task 选检查项。

检查完成 2/4 项，只表达“已验收两项”，不宣称整个里程碑完成 50%。各项工作量与价值不同，范围也可能变化。任务完成数同理，不自动推导完成比例。

里程碑完成建议由用户核对标准后确认；所有检查项通过时可以提示检查整体状态，不自动完成。已完成可以重新打开，取消单列。目标日期已过而尚未完成时，只提示“已过目标日期”，不据此判断失败。

成果的定义应匹配目标：交付目标需要交付符合约定；探索目标可以以“形成有证据的采用/不采用结论”为完成，不要求一定建设系统。两者都不能用读完资料、做满时间或 Task 清零代替成果。

是否需要人工维护“约 60%”等完成比例仍待讨论。如果需要，它应明确标为人工估计并带更新时间，不能由投入小时、任务数或检查项数自动计算，也不汇总成方向完成率。

### 7.2 从日常记录形成轻量进展

里程碑允许一条“进展更新”：做成了什么、下一步、阻碍；均可按需填写，并引用 Task Log、Note 或交付物。方向可以汇总这些成果，也可记录范围层面的重点调整和回顾。

不要求重复填写已有 Task Log。可以直接将日志“记为里程碑进展”，引用原记录，按需补一句结论；或作为验收证据。只有跨任务总结、范围变更、目标层面的决定或无法归入单个 Task 的阻碍才需额外更新。更新不计工时。

标为成果的内容保留来源，日常日志不会全部自动成为成果。Task 或里程碑改归属时，应说明引用如何处理；已确认的历史决定不静默消失，证据链接也不带来第二份时间。

建议里程碑可维护“正常 / 有风险 / 受阻”的当前判断，配原因与更新时间；未填写显示“未评估”。系统可提示“本周未记录投入”“已过目标日期”等事实，但不能根据日志数量或投入变化替用户判断进度健康。

### 7.3 方向回顾

方向回顾关注其下里程碑是否仍然重要、投入是否偏移、哪些成果形成积累，以及下一阶段要优先推进什么。可以保留带日期的回顾记录和当前重点，不新增拥有独立 Task 归属的周期对象。

方向不会随着某个里程碑完成而完成。某项技术能力的具体分享目标完成后，成果留在方向下，用户可以在同一方向继续规划新的里程碑。

### 7.4 LLM 的角色

基础两层管理、统计和进度在 LLM 不可用时仍应完整工作。后续可增加里程碑或方向摘要、归属建议，以及从日志提炼目标或验收内容的草稿。

摘要需有时间范围、来源和更新时间。LLM 不根据投入小时或近期日志猜总体完成百分比，不自动改状态、移动 Task、调整所属方向或确认完成。已有 Task 摘要可以作素材，但不能取代长期成果记录。

## 8. 首版范围

首版建议交付用户四项需求的完整基础闭环：

1. 方向和里程碑的增改查、目标描述、状态与归档恢复。
2. Task 关联里程碑，贯通主要创建/编辑入口；历史任务批量关联、未归属查询及变更影响说明。
3. 两层本周/本月/累计投入、同层对比和逐级明细下钻，与 Report 一致。
4. 以里程碑为主体的总览，结合投入、完成状态、成果、下一步与方向标识；里程碑具备可选完成标准、验收检查项和进展更新，方向页提供汇总与回顾。

同阶段补齐直接相关的 API/MCP 读写能力，保持原 Task 调用兼容。单一归属、历史重分类、状态和进度形式按后续讨论定稿，不能把本稿建议当成已批准实现。数据库迁移、接口细节和快捷键在产品定稿后形成实现方案。

后续再考虑：LLM 摘要/归属建议、多目标时间分摊、加权进度、甘特图/依赖、预算预估、自动提醒和完整知识库。KTLO 下持续事项的表达、每周计划是否需要新增界面仍待确认，不因本稿提出而自动扩展首版。任何新增管理层级均需新的明确需求。

### 8.1 每周工作提升怎样与里程碑结合

用户提供的工作习惯材料建议试行四周，以每周约 100 分钟起步，并明确尚无执行结果。它关注团队了解、问题判断、专业积累和下一步投入，而不是要求增加一套与业务平行的工作。本节记录其产品含义，不复制私人工作讨论的完整内容或公司细节。

两层结构继续不变。长期技术问题可以作为一个候选方向；现有项目、阶段盘点或需要独立验证的问题成为里程碑；每周行动通过 Task、Focus、日志和复盘推进这些目标。

| 试行安排 | 周预算 | 建议承接方式 | 可见产物 |
| --- | --- | --- | --- |
| 日常观察 | 每天 2 分钟，五天共约 10 分钟 | 在当前 Task Log 写三行；没有观察可跳过，不强制每日新建 Task | 发生了什么、影响、尚不知道什么 |
| 团队动态 | 15 分钟 | 更新阶段盘点任务中的相关信息 | 方向、负责人、依赖、阻塞及信息来源 |
| 深入一个问题 | 30 分钟 | 具体问题的分析 Task，关联当前重点里程碑 | 事实、假设、证据缺口、最小下一步 |
| 外部学习或请教 | 30 分钟 | 关联当前问题的学习 Task；查机制/工具、请教同事、看 JD 三选一 | 对当前问题有什么帮助、适用与不适用条件 |
| 周末前复盘 | 15 分钟 | 查看里程碑总览，引用已有记录并写下投入选择；需要计时时再关联合适的复盘 Task | 本周兑现的承诺、新增判断/能力/证据、下周继续或调整什么 |

头一两周将团队动态与深挖合计 45 分钟用于恢复团队概况；不能再额外叠加一个 45 分钟深挖时段。之后按表中节奏进行。每月看 JD 替代当周的学习时段，忙周仅保留 15 分钟复盘，不补欠账，不自动堆积逾期任务。

每周计划是跨现有里程碑组织行动的视图或模板，不成为“方向 → 里程碑 → 周计划 → Task”的新层级。首版可先通过现有 Focus 和一份周复盘记录承接；若用户需要，后续细化“准备本周行动”入口，生成可编辑草稿而非自动批量排期。本轮不创建日历、自动化或真实任务。

可以将四周的试行结果独立管理为探索里程碑，例如“恢复团队概况，并对一个重点问题形成有依据的判断”。完成标准来自材料中的四项检验：了解相关工作与负责人、能解释一个原本模糊的问题、形成循证判断或建议、说明下一步为何值得投入。四周是复盘节点，不因日期到了或做够 400 分钟自动完成。

若问题已是某个交付里程碑的组成部分，优先在原里程碑下添加分析/学习 Task；不要求再建一份同名成长里程碑。只有需要独立目标、验收和投入决策时才单独跟踪探索。

### 8.2 同一份工作支持交付与能力积累

每次周复盘分别回答“兑现了什么工作承诺”和“新增什么判断、证据、复用能力”。二者是对同一批工作的不同评价，不意味着两套重复 Task 或工时。

具体建议：

- 保留一份正式归属和计时，交付成果与能力积累都引用同一 Task、日志、设计说明、验证结果或采用记录。
- 针对已有业务目标的学习和分析直接进入其里程碑，不自动另建笼统的“个人提升”方向。
- 独立的职业探索或团队盘点可以有自己的阶段目标，但不能把所有“为成长做的事”都判作 KTLO。
- 计划的 100 分钟是预算，实际投入依然由工作计时得出；没有独立记录观察时段时，不从整个 Task 的工作时间推算“观察用了多久”。
- 若以后用活动标签查看学习/分析，它属于可交叉筛选的视角，不得与主方向统计再次相加；需要精确区分时，应有独立的真实 Task/时段来源。
- 候选长期定位、早期试点和周习惯都是讨论材料，不视为用户已经启动。推进顺序以最新用户选择为准，不能从早期 GPT 建议直接生成实施计划。

## 9. 首版验收场景草案

以下场景用于检验本稿建议，涉及未确认规则的部分随讨论调整：

1. 创建方向，在其下创建里程碑并关联 Task；日志与计时自动进入里程碑，再汇总至方向，无需重复录入。
2. 同一方向存在多个里程碑：总体概览默认比较各里程碑投入和完成情况；方向页可查看合计及内部投入分布。
3. 同一 Task 连续三天工作，两层均汇总全部记录；每日 Focus 完成一项不误把整个 Task 或里程碑完成。
4. 老任务批量关联后，未归属减少量等于新增里程碑投入，方向汇总同步，与 Report 一致。
5. 按建议整体重分类 Task 时，先展示里程碑和方向历史影响，保存与撤销后两层结果一致；移动里程碑所属方向同样可解释。
6. 有日志但没有工作计时，展示活动和“已记录投入 0”，不把文字长度转成工时。
7. 会议、跨工作日时段、未结束时段、AFK、Focus 日程共同存在时，两层均无新增重复计时。
8. 完成零碎 Task 或勾选部分验收项，不自动产生里程碑百分比；完成、重开、取消和标准变化可追踪。
9. 里程碑完成后，方向仍可继续承接新目标；方向没有整体完成百分比，也不平均下属完成比例。
10. 暂停、结束或归档任一层，不级联修改下层状态、不丢失历史投入；默认列表隐藏的时间仍可在报表解释。
11. KTLO 日常支持如采用持续承接项，不显示成果完成率；其投入仍进入两个层级和全局合计。未归属继续可查。
12. 不关联里程碑的原有工作流与旧 API 继续可用；LLM 断开时四项核心能力仍可操作。
13. 任务全部完成时提供验收提示但不自动完成里程碑；零任务、取消、完成后重开等状态不会生成错误完成结论。
14. 每周 100 分钟模板不增加第三层、不重复计时；忙周简化不会形成自动欠账，四周探索按成果而不是打卡次数验收。

## 10. 下一轮优先讨论

已确认的两层结构、Task 关联第二层、两层统计和总览以里程碑为主体，不再作为开放选择反复询问。接下来优先确定：

1. **完成机制**：是否采用用户确认成果、系统根据任务和证据辅助验收的方案？是否确有人工百分比需求？
2. **KTLO 第二层**：是否接受默认“日常支持”持续承接项，保持 Task 的关联层级，同时不把持续维护计作成果完成？
3. **周节奏**：先用现有 Focus/日志/复盘承接，还是需要轻量的本周行动草稿入口？四周探索目标及候选方向需由用户选择后再创建。
4. **归属与历史**：Task 单主里程碑、里程碑单一方向是否适用；整体纠正归属时历史跟随，工作转向则续建 Task，是否符合实际工作？

字段、页面细节及首版验收规则继续随讨论修订。产品定稿后再形成实现方案并开始实现。
