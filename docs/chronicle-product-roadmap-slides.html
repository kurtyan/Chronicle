01 / 07愿景图
Product Structure

三层产品结构：执行、知识、智能

近期不要把 Chronicle 做成重型项目管理软件。先围绕你的真实工作习惯，建立三个能每天复用的支柱。

每天盯着用

Today Focus

  • 像记事本一样编辑
  • 10-20 分钟工作块
  • 当前项高亮和倒计时
  • 顺延、跳过、完成、重排
  • 降低启动阻力
长期留下来

Notes

  • 从 task log 提炼知识
  • 项目、决策、手册、复盘
  • 任务和日志反向链接
  • 统一搜索和回顾
  • 减少重复理解成本
帮你做转换

Local LLM

  • 生成今日计划
  • 重排剩余时间
  • 任务拆解成小块
  • 总结任务成为 note
  • 日报、周报、回顾
02 / 07产品分层
Near Term MVP

近期最应该先做：今日工作纸条

它不是 plan board 的增强版，而是一个能对抗拖延和注意力漂移的外置执行脚本。

现在正在做
10:15-10:35
写 data integrity test
完成当前 顺延 10m 我卡住了 记录到日志
09:30-09:45 整理昨天遗留事项 09:45-10:05 看 searchService diff 10:05-10:15 休息 10:15-10:35 写 data integrity test 10:35-10:50 跑测试并记录结果 10:50-11:10 总结成 task log
设计原则：UI 像文本，数据可结构化；用户只需要直接改字，不需要进入“管理系统模式”。
03 / 07Day Script 草图
Knowledge Loop

Notes 不是替代日志，而是把日志沉淀成长期知识

task/log 保留原始工作痕迹；note 承载未来还会复用的信息、判断和流程。

任务执行

在 task 里记录过程、进展、命令、问题、决策。

完成回顾

任务完成后触发“是否值得沉淀？”

LLM 提炼

生成 note 草稿、标题、标签、来源链接。

人工确认

你编辑和确认，避免垃圾知识进入长期库。

未来召回

搜索、相关 notes、Ask Chronicle 都能引用它。

关键闭环：工作记录 → 知识提炼 → 来源可追溯 → 后续任务可复用。
04 / 07知识沉淀闭环
LLM Strategy

LLM 策略：API-first，加内置高频工作流

Chronicle 不应该只是接一个聊天框。它应该先稳定数据和 API，再把 LLM 嵌入具体动作。

内置 LLM 工作流Plan Today / Replan / Summarize / Extract Note
Chronicle UIBoard / Today / Notes / Reports / Planner
Chronicle API Core

任务、日志、计划、Notes、搜索、报表都通过同一套本地 API 暴露。

本地 LLM 服务OpenAI-compatible / Ollama / Custom endpoint
外部 Agent / MCP高级 prompt、自动化、跨工具工作流
结论：常用动作做进 Chronicle；探索性自动化交给外部 agent。两者共享同一套 API。
